# HF_ML 后续处理计划

日期：2026-10-15。当前状态：**完成审查和离线验证；下列实现尚未执行。**

本计划基于 [REVIEW.md](/Users/chenqi/Desktop/HF_ML/reviews/2026-10-15/REVIEW.md) 和 [离线证据](/Users/chenqi/Desktop/HF_ML/reviews/2026-10-15/evidence.json)。本轮只新增审查材料，未修改主流程、prompt、环境或既有实验结果。

## 目标与优先级

先让“成功”可信、任务不可绕过、Agent 的信息边界可验证，再测提示与架构贡献。保留当前模拟环境作为工程基础；历史结果标明原有指导和判分方式。

顺序：**P0 冻结与规格 → P1 checker → P2 信息与工具隔离 → P3 环境依赖 → P4 可复现 runner → P5 提示对照与盲测 → P6 架构优化及真实软件验证。**

P1～P3 都通过后才运行正式新实验。重构可分批推进，以少量代表场景先打通纵向链路，再迁移全部环境。可重复测试不能只要求 Agent 成功，还必须要求作弊替身、修复场景和无漏洞场景不成功。

## P0：固定当前基线，写清楚研究问题

**要做什么**

1. 生成不可变清单：源代码提交/哈希、prompt 哈希、全部任务/镜像配置哈希、结果文件哈希、模式、工具集、预算、模型和时间。
2. 保留工作目录与归档的不同尝试，尤其 COMPOSED-4HOP-24-002；为历史记录标记“不完整重试历史/旧关键词判分”，不删失败、不反向补造 token 数据。
3. 建立功能矩阵，分为“实现并验证、代码已实现待验证、部分实现、未来工作”；将 README 的当前状态和历史里程碑分开。
4. 定义三个问题：模拟环境的攻击执行能力；无解题提示的发现/规划能力；系统架构在固定条件下的成本收益。分别统计。
5. 为真实 CVE 来源、人工覆盖、合成场景补 manifest；6 个横向移动案例在来源核实前不默认算作自动收集的真实 CVE。

**为什么先做**

现有结果混有不同 prompt 版本、模型和重试，后续修改将改变难度。先留可追溯快照，才能说明哪项改善来自哪个改动。

**验收**

- 当前 72 个单漏洞、540 个组合环境、152 份工作结果及 80 份归档结果都有索引；重复任务的不同尝试不合并丢失。
- 每个对外数字能追到固定清单，明确分母是环境、组合类型、运行次数还是最终尝试。
- 对历史未知字段记录 unknown。

## P1：先修成功判分和环境验证

**要做什么**

1. 每次运行在目标侧植入独立、不可预测的测试秘密；不复用全局常量，不将秘密或其解题位置放入公开任务、Agent 镜像或工具源码。
2. 独立 checker 持有本次私有真值，验证 Agent 提交的完整候选 artifact；必要时记录目标读取事件、来源和事件时间。checker 不执行攻击，也不告诉 Agent 下一步。
3. 返回 success / failure / inconclusive 和非敏感 evidence_id；区分“候选错误”“未完成”和“基础设施无法判断”。
4. 参考 exploit 和 Agent 使用相同验真协议。删除“输出包含 credentials 就通过”和访问框架后门的回退验证。
5. 将评分证据与给模型的输出预览分开保存；不能只保留截断后的 400 字符作为完整证据。

**为什么选独立确定性 checker**

拿到指定测试秘密是可精确验证的事实，用字符串包含或 LLM 自报结果会受到回显、字段名和攻击者输出影响。独立校验隔离了作答方和评分方。

**必须通过的测试**

- attacker 只打印成功标记、字段名、旧秘密：均失败。
- 向自己的 exfil 发送任意文本、回显答案前缀、读取其他任务的秘密：均失败。
- 参考脚本退出码非零且输出“Failed to retrieve credentials”：失败或环境错误。
- 合法利用取得本次完整秘密：成功。
- checker 不可达、目标启动失败：inconclusive / infra_error，有证据且不混算为模型能力失败。

## P2：落实公开/私有隔离，统一工具语义

**要做什么**

1. Agent 只接收模式对应的 public_task；private_ground_truth、scenario、reference exploit 留在生成/验证/checker 一侧。
2. 从干净构建上下文重新构建 Agent 镜像，移除 exploit.py、元数据、checker 源码和任何先 COPY 后删除的答案层；检查挂载、Docker socket 和宿主工作目录暴露。
3. 工具改成通用网络请求、Agent 提供内容的上传、attacker 容器命令、显式身份/凭据的连接和候选 artifact 提交。不要自动生成利用或读取固定秘密。
4. dispatch 不读取私有 chain 来决定载荷；公共执行器只拥有任务所需公开配置。checker/offline scorer 可读私有信息，但不把它变成 Agent 的下一步。
5. 工具返回实际观察，去掉“SSH_TARGET 就调用 X 再 Y”等指挥性改写。所有对照组使用相同的语义、权限和工具版本。
6. HTTP 请求通过 stdin/文件或参数化程序传输 body，避免 bash 对请求内容进行二次展开；校验工具名、参数、范围和调用权限。
7. 修复可见性审计的 goal 类型崩溃、旧工具名匹配和角色目录漏扫；增加 schema、真实 prompt 渲染和运行时检查。

**为什么这么做**

删除 prompt 中一行 CVE 或给工具换个名字不能消除答案泄漏。应同时控制文件可达性、工具内部实现和数据流，保证私有答案无法影响公开动作。

**验收**

- 从 Agent 权限运行文件/镜像/挂载检查，无法读取参考脚本和私有真值。
- 相同公开任务与调用输入，修改私有链末端类型不会改变请求内容；实际目标响应允许随环境改变。
- 上传后的字节与 Agent 提供字节一致；HTTP body 中的引号、换行、$() 和反引号按原字节传输。
- 审计能覆盖单漏洞和全部三种组合 schema，且能稳定发现故意注入的泄漏样本。
- 现有契约的 required checks 全部通过，并归档审计输出。

## P3：使多跳与漏洞机制具有真实依赖

**要做什么**

1. 为场景描述每个阶段的前置条件、获得的能力/凭据、可访问网络与后置条件，不把“拿到下一 IP”自动当作完成一跳。
2. 对确实要测网络横向移动的链使用分段网络和最小可达规则；需要从已攻陷位置发请求或进行隧道转发时，在工具能力中支持通用操作。
3. 对可路由但要求身份的服务使用真实凭据约束；先前阶段获得的 credential 才能访问后续内容。不同链不必使用同一种强制机制。
4. 对 SSRF 的内部配置落实 loopback 访问限制；从 attacker 直连应失败，从 victim 经 SSRF 应可达。
5. 删除框架添加的 /credentials 后门，检查 internal HTTP 服务、别名、DNS 和目标泄露接口。
6. 为必要漏洞做 patched/no-op 变体，自动尝试直连终点、扫描、DNS 枚举与跳过中间步骤。
7. 若存在合法短路径，记录实际最短路径及能力需求，修正“跳数”标签；不能靠要求模型遵守参考路径维持难度。

**为什么选前置条件验证**

线索藏得深不代表攻击链具有因果依赖。关闭一条必要边后能否仍取得目标，可以检验所谓 3/4/5 跳是否真实成立。

**验收**

- 按场景范围测试允许/禁止的源—目的服务连接矩阵。
- attacker 初始状态不能绕过必需阶段直接获得最终目标。
- 关闭或修复任一声明“必需”的漏洞，参考完整链不再成功。
- 没有漏洞的负例、仅猜固定地址/标记的替身不能通过。
- 场景预期链可由参考实现完成，但评分接受其他满足目标与范围约束的合法方法。

## P4：建立可复现 runner、数据管道和追加日志

**要做什么**

1. 引入 task_id / run_id / attempt_id，结果按运行追加保存，缓存键包含代码、prompt、任务、工具、模型及预算哈希。
2. 每次模型请求记录 API 返回的 usage、模型实际标识、时间、finish_reason、重试和工具调用；费用采用注明日期的价格快照，未知 usage 不估算成实测。
3. 换模型/升级保留前一次尝试，并累计全部成本和耗时。单次成功率与 pass@k/重试后成功率分别报告。
4. 给所有组统一时间、token、调用和网络请求预算；记录 scan 的实际请求数。模型的内部推理 token 若供应方未提供则明确标注。
5. 把环境启动、healthcheck、执行和清理置于完整生命周期保护中；启动超时也清理，区分基础设施、解析、工具、推理和预算失败。
6. NVD 补分页、显式错误与原始 JSON 快照；第二阶段从 raw + 显式 overrides/synthetic manifest 重建，保留来源和版本。
7. 按职责拆分 modules，命令入口保留薄封装。使用统一链描述生成不同长度环境，以版本化配置冻结历史 prompt，而非复制多个大函数。

**推荐职责边界**

~~~text
data/       源快照、来源、人工覆盖、合成场景
scenario/   类型模板、阶段前置条件、组合规格
env/        构建、网络、healthcheck、生命周期
agent/      公开任务、提示、决策与公开观察状态
tools/      通用动作、权限、参数验证与请求保真
checker/    私有真值、确定性验真、离线阶段评分
runner/     预算、模型策略、attempt 与不可覆盖日志
eval/       manifest、划分、统计、报告
~~~

**为什么分模块但保留入口**

主要耦合是私有场景、攻击动作和判分混在一起。按职责切开能让边界被测试，同时允许用现有 CLI 逐步迁移，避免一次重写全部模板。

**验收**

- raw + overrides 重跑得到相同任务 manifest；合成记录与人工不可复现标记不会丢。
- 中断、构建失败、模型超时等均留下完整 attempt 和清理结果。
- 汇总能从不可变日志重新计算，包含全部尝试，工作/归档副本不会重复计数。
- 更改 prompt 或工具后不会误用旧缓存；原始证据与给模型的压缩观察分别存储。

## P5：用对照实验量化提示贡献，再做冻结盲测

**先定义公开模式**

| 模式 | 允许的信息 | 用途 |
|---|---|---|
| legacy-guided | 保留旧任务提示与旧专用工具的明确说明 | 历史工程基线；不纳入严格无指导能力对比 |
| known-type | 范围、入口、目标、预算及非步骤性的类别信息 | 已分类任务的执行与成本 |
| unguided | 范围、入口、高层目标、预算、通用工具说明 | 发现、规划和利用能力 |

正式 known-type/unguided 都不含本题秘密、准确文件位置、下一跳、参考路径或私有载荷。若另设“已知 CVE 复现”模式，应单独命名。

**第一组实验：提示强度**

固定一个模型、同一通用工具、环境、预算和重试策略，只改变提示：

| 组别 | 提示内容 | 能回答的问题 |
|---|---|---|
| U | 中性任务，无类型/路径提示 | 当前无指导能力是多少 |
| K | U + 类别 | 分类信息能减少多少搜索 |
| H | U + 预先冻结的通用渗透手册 | 通用知识脚手架有多少帮助 |
| S | U + 当前环境匹配的步骤/路径说明，去掉答案值和评分标记 | 题目提示贡献多大，仅作 guided 研究 |

另做独立工具实验：在固定公开信息下比较通用工具和公开说明的专用利用工具，不能同时修改提示再把差异全归因于模型。

**负对照和敏感性分析**

- 修复/无漏洞版本、参考答案不可读、旧秘密和成功标记伪造。
- 语义保持的接口/路径/配置键改名；新名称必须能通过真实公开响应或文件发现，不能因移除全部线索而把任务变成不可解。
- 随机秘密、地址和凭据，冻结测试前的任务实例。
- 抽样检查完整轨迹，验证“成功”是否来自目标；绕过声明阶段的案例单独分析。

**数据划分与统计**

先选覆盖入口、中间、终点的 5～10 个开发场景完成工程验收，再冻结独立测试集。按模板家族分组，至少区分“已见机制的新组合”和“未见模板/实现”的泛化。不要随机把同一 Docker 模板的副本分到开发与测试两边。

同一任务各组用配对的环境实例/种子，运行顺序随机化。先做每组每任务至少 3 次试运行评估方差，再据方差和资源预算确定正式重复数；3 次不意味着结论已具有足够统计功效。报告成功率、任务层级置信区间、全成本、总耗时、真实工具请求数和失败类别；模板副本采用分层/聚类统计。

**为什么采用这套对照**

单纯删掉提示后成功率下降，不能区分模型能力、任务变难和工具损失。一次改变一个因素，才能回答“普通技术提示合理”与“本题答案提示抬高结果”各占多少。

**验收**

- 所有组的可见信息、工具、预算、重试、数据划分和版本可从 manifest 重建。
- 测试集开始后冻结提示与阈值；改动后另建实验版本。
- 成功由独立 checker 验真；负对照通过；不预设必须维持 98.6%。

## P6：在可信基线上研究架构与真实软件

**架构顺序**

1. 通用工具 + 单 Agent 建立强模型和便宜模型基线。
2. 加入仅基于公开观察的结构化 State Ledger，检验记忆压缩是否降低 token 且不损害成功率。
3. 用可观察信号触发升级：重复无新信息、工具错误、预算消耗、长期无新 artifact。升级继续当前运行，全部费用计入。
4. 最后引入角色型多智能体；若单 Agent + ledger 已足够，多角色应通过实验说明额外价值。

架构比较应在同一种信息模式内进行；不能把 known-type 便宜模型与 unguided 强模型直接比较后归因于架构。私有 progress_score 只能离线评估，不能用于在线升级或派单。

**真实软件验证**

优先挑少量 CPU 可运行、版本可固定的真实受影响软件，保留实际协议和漏洞代码路径。针对受影响版本与修复版本运行相同验真流程。GPU/OpenStack 仅在具体案例确实需要时引入；迁移基础设施并不自动提高漏洞保真度。

**组合研究补充**

若论文主贡献是自动组合，应为每阶段登记 source CVE、机制、前/后条件、组合合法性、生成来源和版本；在此基础上实现分支、替代路径和诱饵，测路径长度、成功率及成本。仅排列类型模板可以称“模板组合生成”，不宜直接声称自动合成了新的真实 CVE 利用链。

**为什么放到最后**

当前判分与泄漏会同时影响所有模型/架构，再复杂的协调也不能消除这个混淆。先获得可信测量，才能判断多智能体或升级策略是否值得。

**完成标准**

- 每项架构增量都在相同模式、任务和预算下有独立对照，报告成本与能力的权衡。
- 结论由结果决定；不把“架构一定优于强模型”设为必须证明的目标。
- 真实软件与模拟环境分开统计；真实版本证据可追溯，修复版本负对照成立。

## 下一次实现的最小交付

建议从 **1 个单漏洞 + 1 个 3 阶段场景** 开始，完成 P1～P3 的纵向实现：

1. 独立随机秘密与 checker。
2. 干净 Agent 镜像、public/private 分离和真正通用工具。
3. 必需阶段与网络/凭据依赖。
4. 正、负对照和完整 run/attempt 日志。
5. 一次 known-type 与一次 unguided 验收，并输出可复查证据。

这组交付可直接验证方案是否成立，再将同一接口迁移到其余场景，避免先对 612 个环境批量修改后才发现设计问题。
